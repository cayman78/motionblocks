# Glossary

## Stofendez Lab

The project laboratory / team brand.

## MotionBlocks

The main project.

A wearable motion intelligence system that collects, labels, stores, analyzes, and later classifies human motion patterns.

Current hardware target:

```text
M5StickC Plus2
```

Current working mode:

```text
wearable device → Wi-Fi HTTP batch logger → CSV files → metadata → analysis
```

---

## MotionLink

Future technology layer for linking the personal motion domain to external dashboards and Human-by-Wire domains.

In the current prototype, MotionLink is only a future concept.  
The current working transport is Wi-Fi HTTP batch logging.

---

## Human-by-Wire

A broader architectural idea where human-related domains can be represented as connected digital domains.

MotionBlocks may later become a personal motion domain inside this architecture.

---

## Motion block

A labeled motion pattern.

Examples:

```text
idle
walking
standing up
sitting down
jumping
shaking hand
fall-like event
unusual motion sequence
```

Motion blocks are the future semantic units for comparison, classification, and pattern recognition.

---

## Motion domain

A personal domain that owns and processes motion-related data, metadata, events, and derived features.

In the current prototype, the motion domain is represented by:

```text
raw CSV files
metadata JSON files
future feature files
future analysis outputs
```

---

## Experiment

A logical data collection activity.

Example:

```text
EXP01 — ordinary home movements
```

An experiment groups devices, sessions, subjects, movements, raw files, and metadata.

Current metadata file:

```text
data/metadata/experiments.json
```

---

## experiment_id

A short technical identifier for an experiment.

Examples:

```text
EXP01
EXP02
EXP03
```

The human-readable name of the experiment is stored separately in metadata fields such as:

```text
short_name
title
goal
comments
```

---

## Device

A physical sensor device used for recording motion.

Current device:

```text
M5StickC Plus2
```

Example device id:

```text
m5_001
```

---

## device_id

A project-level technical identifier assigned outside the firmware by the logger or metadata layer.

Example:

```text
m5_001
```

The firmware does not know `device_id`.

Current device identity rule:

```text
firmware reports technical identity
logger resolves or validates device_id
```

Related: `DEVICE_INFO`, `mac_address`, `devices.json`.

---

## DEVICE_INFO

A protocol event that reports technical device identity from firmware to the logger.

Current format:

```csv
EVENT,DEVICE_INFO,mac_address,firmware_version,timestamp_ms
```

Example:

```csv
EVENT,DEVICE_INFO,F0:24:F9:97:ED:08,motionblocks.logger.v0.6.2,6972
```

The logger can use this event to resolve or validate `device_id`.

---

## mac_address

A hardware network identifier reported by the device and used for device registry lookup.

Example:

```text
F0:24:F9:97:ED:08
```

In MotionBlocks, `mac_address` is a technical identity signal.  
It is not the same as project-level `device_id`.

---

## devices.json

Metadata file used as the device registry.

Current path:

```text
data/metadata/devices.json
```

Typical purpose:

```text
map mac_address → device_id
store device name / model / status
```

---

## Recording session

A group of records collected under one device-local session id.

In the current firmware, sessions are controlled by Button B.

Examples:

```text
A001
A002
A003
```

Important current limitation:

```text
A device reset can make the firmware start again from A001.
```

Therefore a recording session id alone is not sufficient as a unique file identity.

Related: `device_session_id`, `recording_run_id`, `safe file name`.

---

## session_id

A short session identifier generated by the device.

Examples:

```text
A001
A002
A003
```

The device knows `session_id`.

Current recommendation:

```text
Use device_session_id when the text needs to make clear that the id comes from firmware.
```

---

## device_session_id

The session id generated by the firmware.

Examples:

```text
A001
A002
A003
```

`device_session_id` is introduced to avoid ambiguity around `session_id`.

Important distinction:

```text
device_session_id = device-local session id
recording_run_id  = logger-side unique run id
```

The firmware owns `device_session_id`.  
The logger / data layer owns `recording_run_id`.

---

## session_uid

A metadata identifier previously used to identify a session.

Earlier format:

```text
[experiment_id]_[device_id]_[session_id]
```

Example:

```text
EXP01_m5_001_A001
```

Current limitation:

```text
This is not safe if the same device resets and emits A001 again in the same experiment.
```

Future metadata should use or include `recording_run_id` to avoid ambiguity.

---

## recording_run_id

A logger-side unique identifier of a physical recording run.

Example:

```text
run_0001
run_0002
run_0003
```

This id is assigned by the logger / data layer, not by firmware.

Purpose:

```text
prevent repeated device-local sessions such as A001 from overwriting or mixing data
```

Related: `device_session_id`, `safe file name`.

---

## Record

One recorded attempt inside a recording session.

In the current firmware, a record starts when Button A is double-clicked and stops when Button A is clicked during recording.

Current field:

```text
record_id
```

Important distinction:

```text
RecordingSession → contains one or more Records
Record → contains many MotionSamples
```

---

## record_id

A numeric identifier of a record inside a session.

Example:

```text
1
2
3
```

When the session changes, `record_id` resets to `1`.

---

## Motion sample

One timestamped IMU measurement row inside a record.

Current fields include:

```text
sample_id
device_timestamp_ms
ax
ay
az
gx
gy
gz
acc_norm
```

---

## sample_id

A numeric identifier of a sample inside a record.

It increments while recording is active.

---

## device_timestamp_ms

Timestamp generated by the device, measured in milliseconds.

It is used to order samples and to estimate actual timing properties such as:

```text
dt_ms
effective_sample_rate_hz
gaps
```

---

## IMU

Inertial Measurement Unit.

A sensor block that includes:

```text
accelerometer
gyroscope
```

Current IMU fields:

```text
ax
ay
az
gx
gy
gz
```

---

## Accelerometer

Sensor that measures acceleration along device axes.

Current acceleration fields:

```text
ax
ay
az
```

Units:

```text
g
```

In rest position, the accelerometer still measures gravity.

---

## Gyroscope

Sensor that measures angular velocity around device axes.

Current gyroscope fields:

```text
gx
gy
gz
```

Units:

```text
deg_per_sec
```

---

## acc_norm

Derived acceleration magnitude.

Formula:

```text
acc_norm = sqrt(ax*ax + ay*ay + az*az)
```

In rest position, `acc_norm` should be close to:

```text
1.0 g
```

This metric is useful because it is less sensitive to device orientation than individual acceleration axes.

---

## gyro_norm

Derived angular velocity magnitude.

Typical formula:

```text
gyro_norm = sqrt(gx*gx + gy*gy + gz*gz)
```

This is planned as a useful analysis feature.

---

## Serial logger

Python tool for wired logging over USB Serial / COM port.

Current file:

```text
tools/serial_logger.py
```

Typical command:

```powershell
python tools/serial_logger.py --port COM6 --experiment-id EXP01 --device-id m5_001 --create-metadata
```

Status:

```text
working / useful for debugging
```

---

## HTTP logger

Python tool for wireless logging over Wi-Fi HTTP.

Current file:

```text
tools/http_logger.py
```

Typical command:

```powershell
python tools/http_logger.py --host 0.0.0.0 --port 8080 --experiment-id EXP01 --device-id m5_001 --create-metadata
```

Current capabilities:

```text
receive one protocol line
receive newline-separated protocol batches
write raw CSV files
create draft metadata
handle DEVICE_INFO
handle SAMPLE_RATE
resolve / validate device_id
```

Status:

```text
working / main path for wearable recording
```

---

## HTTP endpoint

A URL path exposed by the HTTP logger.

Current endpoints:

```text
GET  /health
POST /line
```

`GET /health` checks whether the logger is alive.

`POST /line` receives either:

```text
one MotionBlocks protocol line
```

or:

```text
a newline-separated batch of MotionBlocks protocol lines
```

---

## HTTP batch mode

Current wireless transport mode where multiple `DATA` rows are sent in one HTTP POST body.

In this mode:

```text
service events are sent immediately
DATA rows during recording are batched
STOP flushes pending DATA before sending STOP
```

Current batch parameters:

```text
25 DATA rows per batch
500 ms maximum batch age
```

HTTP batch mode does not change the MotionBlocks protocol.

It only changes how protocol lines are transported.

---

## DATA batch

A newline-separated group of `DATA` protocol rows sent in one HTTP POST body.

Example shape:

```text
DATA,...
DATA,...
DATA,...
```

The logger processes a batch by splitting the body into individual lines.

---

## LOGGER_URL

Firmware configuration value pointing to the Python HTTP logger endpoint.

Example:

```cpp
#define LOGGER_URL "http://192.168.8.129:8080/line"
```

It is stored in local `wifi_config.h`.

---

## wifi_config.h

Local firmware configuration file containing real Wi-Fi credentials and logger endpoint.

Current path:

```text
firmware/m5stickc-plus2/src/wifi_config.h
```

Contains:

```cpp
WIFI_SSID
WIFI_PASSWORD
LOGGER_URL
```

This file must not be committed to Git.

---

## wifi_config.example.h

Version-controlled example of Wi-Fi configuration.

Current path:

```text
firmware/m5stickc-plus2/src/wifi_config.example.h
```

Used as a template for local `wifi_config.h`.

---

## MotionBlocks protocol

Simple line-based protocol sent by the firmware through Serial and HTTP.

Current lines:

```csv
EVENT,DEVICE_INFO,mac_address,firmware_version,timestamp_ms
EVENT,SAMPLE_RATE,sample_rate_hz,timestamp_ms
EVENT,NEW_SESSION,session_id,timestamp_ms
EVENT,START,session_id,record_id,timestamp_ms
DATA,session_id,record_id,sample_id,timestamp_ms,ax,ay,az,gx,gy,gz,acc_norm
EVENT,STOP,session_id,record_id,timestamp_ms,sample_count
```

The protocol is intentionally stable across transports.

HTTP batch mode does not change the protocol.

---

## EVENT row

A protocol row describing a recording or configuration event.

Current event types:

```text
DEVICE_INFO
SAMPLE_RATE
NEW_SESSION
START
STOP
```

EVENT rows are stored in the same CSV files as DATA rows.

---

## DATA row

A protocol row containing one IMU sample.

Current DATA format:

```csv
DATA,session_id,record_id,sample_id,timestamp_ms,ax,ay,az,gx,gy,gz,acc_norm
```

In HTTP batch mode, multiple DATA rows may be transported together inside a DATA batch.

---

## SAMPLE_RATE

A protocol event that reports the sampling rate selected on the device.

Current format:

```csv
EVENT,SAMPLE_RATE,sample_rate_hz,timestamp_ms
```

Example:

```csv
EVENT,SAMPLE_RATE,100,7200
```

The value reported by this event is the configured / selected sampling rate, not necessarily the measured effective rate.

---

## Raw CSV

The current raw data storage format.

Current path convention:

```text
data/raw/[experiment_id]/[device_id]/session_[session_id].csv
```

Current limitation:

```text
session_[session_id].csv is not safe across device resets
```

Target next naming direction:

```text
data/raw/[experiment_id]/[device_id]/run_0001_session_A001_100Hz.csv
```

CSV is used because it is easy to inspect, plot, and explain.

---

## safe file name

A raw data filename that encodes enough identity to prevent accidental overwriting or mixing of repeated device-local sessions.

Example target form:

```text
run_0001_session_A001_100Hz.csv
```

Safe file names are part of data identity, not cosmetic naming.

---

## Metadata

Human-readable JSON files that describe experiments, devices, and recording sessions.

Current metadata files:

```text
data/metadata/experiments.json
data/metadata/recording_sessions.json
data/metadata/devices.json
```

Metadata stores semantic information that the firmware does not know:

```text
subject_id
movement_type
movement_label
location
comments
status
```

```text
auto created. needs description.
```

Draft records should later be reviewed and completed manually.

Examples:

```text
child_01
child_02
adult_01
```

---

## subject_id

Stored in metadata, not in firmware.

## movement_type

```text
idle
walking
jumping
shaking
fall_like
unknown
```

Stored in metadata.

## movement_label

Examples:

```text
standing_idle
walking_normal
jumps_basic
hand_shaking
sitting_to_standing
```

Stored in metadata.

## Data status

Examples:

```text
auto created. needs description.
raw

```

## Generated data

Local data created by loggers and analysis scripts.

Examples:

```text
data/raw/

data/db/
```

Generated data should normally be ignored by Git unless intentionally added as examples.

---

## Sampling rate

Frequency of IMU data collection.

Current selectable rates:

```text
5 Hz
10 Hz
25 Hz
50 Hz
100 Hz
```

Current default:

```text
10 Hz
```

The selected sampling rate is reported through `EVENT,SAMPLE_RATE`.

Related: `sample_rate_hz`, `configured sample rate`, `effective_sample_rate_hz`.

---

## sample_rate_hz

Metadata and protocol field containing the configured / selected sampling rate.

Example:

```text
100
```

Important rule:

```text
sample_rate_hz is not automatically equal to effective_sample_rate_hz
```

---

## configured sample rate

The sampling rate selected on the device and reported by `EVENT,SAMPLE_RATE`.

It is the intended sampling frequency.

It should be stored as:

```text
sample_rate_hz
```

---

## effective_sample_rate_hz

The measured sampling rate calculated from recorded DATA timestamps.

It is an analysis result, not firmware truth.

Typical calculation:

```text
effective_sample_rate_hz = (N - 1) / duration_sec
```

This value is used to check whether the configured rate was actually achieved.

---

## dt_ms

Time interval in milliseconds between two adjacent DATA samples.

Typical calculation:

```text
dt_ms[i] = device_timestamp_ms[i] - device_timestamp_ms[i-1]
```

`dt_ms` is useful for detecting gaps, jitter, and effective sampling rate problems.

---

## gap

A suspiciously large interval between adjacent DATA samples.

Gaps are detected from `dt_ms`.

The exact threshold may depend on the configured sample rate.

---

Planned analysis output summarizing recording quality across sessions or recording runs.

Possible fields:

## quality_status

Planned analysis field describing the quality of a recording.

Possible values:

```text
OK
WARN_GAPS
WARN_SHORT
WARN_RATE_MISMATCH
```

## Feature

A derived value calculated from raw motion samples.

Examples:

```text
acc_norm_max
acc_norm_mean
acc_norm_std
gyro_norm_max
record_duration
sample_count
effective_sample_rate_hz

```

Features should be computed later in Python analysis scripts.

---

## Experimental IMU-only displacement feature

Future experimental feature based on approximate trajectory reconstruction from IMU data.

Examples:

```text
estimated_path_length
estimated_displacement_norm
estimated_vertical_displacement
vertical_drop_score
```

These are not reliable physical coordinates.  
They may be useful as weak features for fall-like classification.

## FDAM compatibility

The current structure is simple but should remain compatible with a future FDAM-style motion domain.

Current practical hierarchy:

```text
Experiment
  → RecordingSession
      → DataFile
      → MotionRecord
          → MotionSample
              → Sensor values / channels
```

Children should not be exposed to FDAM concepts directly.
